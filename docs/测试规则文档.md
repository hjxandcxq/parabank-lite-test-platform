# ParaBank 测试平台 — 测试规则

## 1. 用例编号规则

格式：`<模块>_<序号>`；模块为 LOGIN（登录）/ REG（注册）/ TRAN（转账）

- 登录、注册、转账统一用 3 位序号（`LOGIN_001`、`REG_002`、`TRAN_001`）
- 编号同时作为 pytest 参数化 ID，节点形如 `test_login.py::test_login[LOGIN_001]`、
  `test_transfer.py::test_transfer[TRAN_001]`，平台按该节点把执行结果回填到对应用例
- 用例表以《ParaBank Lite 业务规则与测试用例设计（最新版）》与
  《等价类划分与测试用例.xlsx》为准，落地版见 `docs/测试用例设计.md`
  （由 `testcase_spec.py` 生成，共 60 条：登录 19 + 注册 22 + 转账 19；
  其中 LOGIN_016~019 为登录图形验证码的扩展用例）

## 2. 用例优先级

| 级别 | 判定标准 | 执行频率 |
|------|---------|---------|
| P0 | 核心主流程，失败阻断业务 | 每次提交 |
| P1 | 重要功能，影响体验 | 每日 |
| P2 | 边缘场景、UI 细节 | 每周 |

## 3. 用例分类

| 分类 | 说明 | 示例 |
|------|------|------|
| 功能 | 业务功能正确性 | 转账金额正确扣除 |
| 运营 | 用户流程、转化节点 | 新用户从注册到完成首笔转账 |
| UI | 页面元素、布局、提示 | 错误提示文案是否清晰 |
| 异常 | 输入校验、边界、错误处理 | 转账金额输入负数 |

## 4. 结果判定规则

- **PASS**：所有断言通过，且页面反馈符合预期
- **FAIL**：断言失败（业务不符）
- **ERROR**：脚本异常（元素找不到、超时、驱动问题）
- **SKIP**：前置条件不满足（如依赖数据不存在）

一条用例的执行结果只允许是以上四者之一。

## 5. 失败归因规则

| 失败类型 | failure_reason 前缀 | 处理责任 |
|---------|--------------------|---------|
| 断言失败（业务不符） | ASSERT_ | 开发 |
| 元素/超时 | TIMEOUT_ / NOELEMENT_ | 测试（脚本问题或 UI 变更） |
| 网络 | NETWORK_ | 运维 / 环境 |
| 驱动 | DRIVER_ | 环境 |

## 6. pytest 套件规则

每个独立 pytest 项目放在 `pytest_suites/<name>/` 下，必须：

1. 包含 `conftest.py`，定义 driver fixture；会话开始前调用
   `parabank_lite.reset_demo_data()` 重置预置演示数据
2. 用例数据全部取自 `testcase_spec.py`，不在用例里另写测试数据
3. 使用 `pytest-json-report` 插件输出 json
4. 参数化 ID 必须是用例编号（如 `[LOGIN_001]`），与平台 `test_cases.pytest_node` 一致
5. 被测地址取 `browser_setup.BASE_URL`（默认 `http://127.0.0.1:5000/parabank`）
6. 运行命令统一为：
   ```
   python -m pytest pytest_suites/<name>/ --json-report --json-report-file=reports/<run_id>.json
   ```

## 6.1 一致性维护

- `testcase_spec.py` 是业务规则、用例表、预置数据的唯一来源
- 用例断言与被测系统 `parabank_lite.py` 使用同一段提示文案
- 用例表变更后必须执行：
  ```
  python gen_case_doc.py          # 重新生成 docs/测试用例设计.md
  python check_consistency.py     # 校验 用例表/被测系统/平台库/pytest/文档 五方一致
  ```
- 平台上填写的执行参数（用户名、金额等）以 `PB_<字段名>` 环境变量覆盖该套件
  所有用例的对应字段，仅用于手工试错；这类执行的 `triggered_by` 记为 `web+params`，
  不参与"失败集合 == 缺陷清单"比对（只认 `web` 的标准执行）
- 用例对提示文案做**全等匹配**：`expect_msg` 必须与被测系统返回的文案完全一致
  （服务端模板直接渲染 `{{ error }}`，不含装饰），避免"包含匹配"漏掉多余前缀后缀
- 平台库由 `app.py` 的 `SEED_VERSION` 触发重建，用例数变化无需手工改库

## 7. 报告生成规则

- 每次运行生成一个 `suite_runs` 记录
- 每条用例生成一条 `test_results` 记录
- 失败用例必须写入 traceback 与 screenshot_path（如可获取）
- 通过率 = passed / total * 100%，保留 1 位小数

## 8. 数据保留

- `suite_runs` 保留最近 200 条
- `test_results` 保留最近 30 天
- 截图保留最近 30 天

## 9. 触发规则

- 手工验证（"执行测试"页）：自己填参数 → 点"执行一次"，由 pytest
  （`pytest_suites/manual_suite`）+ Selenium 无头浏览器跑**一次**真实操作。
  留空的字段用预置值：登录 = alice01/Pass123；注册 = Pass123，
  用户名留空则平台自动造一个新用户（"假装新用户"）；转账 = 10001→10002/100 元。
  判定口径按"这次操作**实际**成没成"（不做文档断言）：
  - 注册：账号已在库里创建 → PASS；页面给了错误提示 → FAIL（原因 = 系统提示原文）；
    账号最终没创建 → FAIL
  - 转账：源账户余额已按金额变化 → PASS；页面给了错误提示 → FAIL；
    余额没变 → FAIL
  - 登录：已进入账户概览 → PASS；页面给了错误提示 → FAIL；既没跳转也没提示 → FAIL
  系统提示原文一律写入 `test_results.actual_result`（"结果明细"的"实际提示"列）。
  `triggered_by = manual`，不进首页通过率统计，也不参与"失败集合 == 缺陷清单"比对。
- 整套件回归（"测试套件"页）：点"执行整套件"跑该套件全部用例（有文档断言）
- 全部执行：三个套件各点一次"执行整套件"
- 并发限制：同一时刻同一套件只能有一个 RUNNING 状态（手工验证不占用该限制）
